# Fixed Homogeneous 3v3 Environment Audit

This report audits only the current fixed homogeneous 3v3 UAV combat environment. It does not use 1v1 or 2v2 as learnability evidence, does not implement 3v2 or heterogeneity, and does not change rewards, observations, dynamics, MAPPO, or blue rules. The executable evidence is generated by `scripts/audit_3v3_environment.py` into `outputs/audit/3v3_environment_audit.json` and `.csv`.

## Evidence base

Primary paper: Zheng, Wei, and Duan, 2024, *UAV swarm air combat maneuver decision-making method based on multi-agent reinforcement learning and transferring*. The audit used the project-root PDF and checked the extracted definitions for the 3-DoF model, 15-action library, local/global state spaces, attack conditions, damage model, situation/event/dense/end-game rewards, and Algorithm 2. The 2023 paper is only auxiliary for inherited 1v1 reward conventions and is not used as 3v3 performance evidence.

## Classification summary

### paper_defined

- Three-degree-of-freedom overload point-mass model: implemented by `uav_env.dynamics.point_mass_3d.point_mass_3d_derivative`.
- Fifteen discrete maneuvers: implemented by `uav_env.actions.discrete_15`.
- Attack conditions and attack/escape angles: implemented by `uav_env.combat.attack_geometry.compute_combat_geometry`.
- Piecewise damage distribution and blood depletion: implemented by `uav_env.combat.damage`.
- Local state block structure from equation (9): implemented as a fixed 45D 3v3 adaptation by `uav_env.observations.multi_observation`.
- Global state equation (10): implemented as fixed 87D 3v3 adaptation by `uav_env.observations.global_state`.
- Situation reward equations (12)--(19): implemented by `pair_situation_reward` and `individual_situation_reward`.
- Event reward Table 2: implemented by `CombatMultiEnv._event_reward`.
- Dense reward assignment Algorithm 2: implemented by `assign_dense_rewards`.
- End-game reward equations (21)--(25): implemented by `multi_terminal_reward_allocations`.

### project_defined

- Fixed homogeneous 3v3 head-on formation is a project experiment; the 2024 paper's formal scale includes heterogeneous 3v2 transfer, which is not implemented here.
- Initial geometry is fixed: red x=-900, blue x=+900, y positions -500/0/500, z=1800, speed=110, headings 0 and pi.
- Blue opponent is `PursuitOpponent`, a fixed geometric pursuit rule, not the paper's full predictive threat script.
- Simultaneous multi-attack resolution, overkill accounting, and destroy-credit tie breaking are project-defined to remove traversal-order dependence.
- Fixed-slot MAPPO outputs always keep red_0/red_1/red_2, with dead slots masked and rewards zero between destruction and terminal allocation.
- The Algorithm 2 damaged branch keeps the literal paper value as `paper_value` but caps it by `damage_penalty=-r_den0*nr` so damaged UAV assigned dense reward is strictly negative. This is an explicit project assumption resolving a formula/text conflict, not a claim of verbatim paper formula.
- Timeout survivor-count wins are reported separately from elimination wins.

### unresolved

- The 45D Actor observation omits own and enemy health; controlled pairs with health 300 vs 1 are identical to the Actor.
- `relative_pitch` and `relative_yaw` are global line-of-sight angles from `atan2`, not body-relative bearing angles after subtracting own attitude.
- Enemy and ally local observation blocks are distance-ranked; small distance crossings can swap entity identity presented to a plain MLP.
- The 87D Critic state omits health values, blue damaged flags, and blue last actions; blue alive/dead with unchanged pose is indistinguishable.
- Dead blue geometry can remain in Critic pair blocks when frozen positions differ.
- Timeout survivor-count win currently calls the same win formula as elimination win; this must be reported separately and remains semantically unresolved for a formal "destroy all blue UAVs" objective.
- Rule-vs-rule diagnostics show pursuit-vs-pursuit and straight-vs-pursuit time out 100/100 with no attacks, so they demonstrate reachability limitations, not learnability.

## Executable audit results

The latest successful run reported 13 checks, 0 failures, and 4 warnings:

- `local_observation`: P1 unresolved.
- `global_state`: P1 unresolved.
- `slot_stability`: P1 project-defined warning.
- `terminal_semantics`: P1 unresolved.

Configuration parsing passed:

- red_count=3, blue_count=3.
- physics_dt=0.1, decision_dt=0.5, physics_steps_per_action=5.
- max_episode_seconds=200, max_decision_steps=400.
- local observation dimension=45.
- global state dimension=87.
- action count=15.
- initial health=300.
- attack distance [40,900], attack angle max 0.5235987756, escape angle max 1.0471975512.

Initial scene passed:

- red x=-900, blue x=+900.
- y positions -500, 0, 500.
- z=1800, speed=110.
- red heading 0, blue heading pi.
- same-team distances are nonzero: 500, 1000, 500 for each side.

Dynamics and action checks passed:

- acceleration increases speed; deceleration decreases speed.
- climb increases flight-path angle; dive decreases it.
- level hold keeps horizontal initial speed and altitude effectively constant.
- left and right turn are mirror-consistent after angle normalization.
- all action propagation results are finite.

Attack and damage checks passed:

- attack distance boundaries at 40 and 900 are inclusive.
- distance 39 and 901 cannot attack.
- attack and escape threshold checks flip at threshold + 1e-6.
- damage samples map to 51, 21, 11, 0 for the four probability intervals.
- effective damage never exceeds remaining health; overkill is recorded.
- expected nominal damage is 15.8.

Observation findings:

- Actor cannot distinguish own health 300 vs 1.
- Actor cannot distinguish enemy health 300 vs 1.
- Actor can distinguish enemy alive vs dead because dead blocks are zeroed and masks change.
- `relative_yaw` is global line-of-sight `atan2(dy,dx)`, not body-relative bearing.
- Dynamic distance sorting can swap true UAV identities between enemy slots.

Global state findings:

- Critic cannot distinguish blue_0 alive vs dead if pose is unchanged.
- Critic cannot distinguish red health 300 vs 1.
- Critic cannot distinguish blue health 300 vs 1.
- Critic cannot distinguish blue last action changes.
- Dead blue frozen position still changes pair-block geometry.
- These are Markov sufficiency risks for a centralized value function and remain unresolved.

## P0/P1/P2 list

### P0

No P0 failures were produced by the executable audit. P0-pass areas include fixed dimensions/timing, initial scene, dynamics/action finiteness, attack geometry, damage distribution, reward lifecycle, and MAPPO adapter shapes.

### P1

- Actor health aliasing: local observation omits health.
- Critic Markov risk: global state omits health, blue damaged flag, and blue last action.
- Dynamic distance-ranked local slots can swap true entity identity for a plain MLP.
- Timeout survivor-count win/loss uses full win/lose terminal formulas and must be reported separately from elimination.
- The damaged dense branch negative cap is project-defined, not a verbatim Algorithm 2 formula.
- The pursuit opponent is a project geometric rule, not the full paper predictive script.

### P2

- MAPPO is a shared feed-forward CTDE baseline, not the paper's three-subnetwork Actor with transfer.
- No attention, GRU, self-play, heterogeneity, or 3v2 is implemented.
- Rule probes are useful reachability diagnostics but not learnability validation.

## V2 upgrade audit addendum

The V2 upgrade keeps the legacy 45D/87D interface available, but adds a separate fixed homogeneous 3v3 schema:

- `environment_schema_version: homogeneous_3v3_v2_timeaware`
- `observation_schema: fixed_id_body_time_63d`
- `global_state_schema: full_entity_time_61d`
- `reward_profile: project_3v3_v2`
- `scenario_profile: head_on_mirrored_jitter_v2`

V2 local observations are 63D: own-state fields plus `episode_progress`, two fixed red ally slots, and three fixed blue enemy slots. Relative position and velocity are expressed in the observer body frame, headings are represented with sine/cosine, health ratios are observable, and dead entity normalized slots use `alive_flag=-1` with all remaining fields zero. Debug metadata also exposes per-red feature names with true entity IDs.

V2 global state is 61D: six fixed entities ordered `red_0..red_2, blue_0..blue_2`, with alive flag, health ratio, absolute position, speed, flight-path angle, heading sine/cosine, and last action, followed by one global `episode_progress` field. Dead entity normalized blocks are represented by `alive_flag=-1` and nine following zeros.

The V2 reward path uses `shape_raw = situation + geometry_event` for Algorithm 2 assignment. Combat event rewards bypass Algorithm 2 and are added directly. Timeout terminal reward uses profile `project_3v3_v2_timeout`; simultaneous elimination uses `project_3v3_v2_simultaneous_elimination`; elimination terminal rewards continue to use `paper_2024_exact`.

The updated audit script records both legacy findings and V2 checks. Legacy warnings are preserved as historical compatibility findings; they do not apply to the formal time-aware V2 63D/61D interface. The earlier 62D/60D V2 smoke schema is considered a development checkpoint schema, is not runnable, and is intentionally rejected by full resume into time-aware V2.

For time-aware V2, timeout is a true finite-horizon terminal state for training even though the Gymnasium API reports it as `truncated=True`. The MAPPO rollout path uses an explicit truncation bootstrap mask: V2 timeout has mask zero and does not bootstrap, while legacy truncation can still use terminal-state bootstrap. The audit also checks that real step 400 retains progress `1` in `terminal_steps` and that the auto-reset next state returns to progress `-1`.
